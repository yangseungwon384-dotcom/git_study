## 1. 범위와 기본 결정

### 반드시 구현할 기능

1. 전체 화면에 일관된 다크 테마와 밝은 테마 전환.
2. 왼쪽 사이드바와 홈·카메라·알림·이벤트 로그·스냅샷·AI 보조 판단·설정 화면.
3. 카메라 1·4분할, 상세 보기, 기존 ROI 편집 기능 연결.
4. 사건 ID를 기준으로 저장되는 알림 확인 상태와 메모·오탐 표시.
5. 날짜·카메라·심각도·확인 상태별 로그 검색.
6. 복원 가능한 로그 목록 비우기와 스냅샷 목록 비우기.
7. 큰 스냅샷 전용 화면, 확대, 사건 상세 연결.
8. 탐지 후보 확인과 경계 흔들림 처리 등 오탐 억제.
9. 기존 데이터 마이그레이션, 의미 있는 테스트, 실행 문서.

### 추가 확인 없이 사용할 기본안

- 초기 테마: 다크. 브라우저별 선택을 보존하며 밝은 모드 전환 제공.
- ‘로그 초기화’: 종료되고 확인된 사건을 기본 목록에서 보관 처리. 복원 가능.
- ‘스냅샷 초기화’: 종료되고 확인된 사건의 사진을 갤러리에서 보관 처리. 파일은 유지.
- 필터 초기화는 검색 조건만 되돌리는 별도 버튼.
- 로그인 체계가 없다면 운영자 확인 시각을 저장하고, 입력한 이름은 미인증 표시명으로 취급.
- 새 모델 학습, 강화학습, 외부 알림 발송, 신규 인증 시스템, 영구 삭제는 이번 범위 밖.
- 기존 실행 옵션과 기본 JSON 준비 모드를 유지. AI를 켜는 옵션을 사용했을 때만 해당 제공자 호출.

이 기본안으로 개발을 진행하라. 소소한 배치·모듈 이름 때문에 작업을 멈추지 말고 선택 근거를 기록하라.

## 2. 기존 코드와 데이터 보존

- 미커밋 변경을 확인하고 사용자의 작업을 덮어쓰거나 되돌리지 마라.
- 진입 파일은 유지하고 필요한 코드만 같은 디렉터리의 모듈로 분리하라. 매번 새로운 final 파일을 생성하지 마라.
- 기존 Gradio 기반 구현을 활용하라. 전체 프런트엔드 교체는 요구하지 않는다.
- 설치된 Gradio 버전·컴포넌트·이벤트 API를 확인하고 지원되는 방식으로 구현하라. 존재하지 않는 API를 추측하지 마라.
- 원본 `zoo_vision.py`, `zoo_safety.py`는 가능한 한 수정하지 않고 어댑터로 연결하라.
- 실제 운영 DB·스냅샷으로 초기화 기능을 시험하지 마라. 테스트용 별도 data-dir과 DB 복사본을 사용하라.
- DB 변경 전 SQLite의 일관된 백업 방식을 사용하고 버전 기반 마이그레이션을 작성하라. 열린 WAL DB를 파일 하나만 복사해 완전한 백업으로 간주하지 마라.
- 스키마 확장 시 `INSERT INTO ... VALUES(...)` 등 컬럼 수에 의존하는 기존 구문을 점검하고 명시적 컬럼 목록으로 수정하라.
- 기존 카메라, ROI, 사건, 판단 이력, 스냅샷 경로가 마이그레이션 후에도 유지되어야 한다.

## 3. 관제 처리 원칙

```text
영상 → YOLO 탐지 후보 → 후보 품질·지속성 확인
     → 동물 이탈 / 사람 진입 규칙 → 기본 사건·경고
     → JEV 또는 Ollama 보조 판단 → 운영자 확인·메모
```

- JEV 결과가 기본 경고 생성의 필수 조건이 되면 안 된다.
- JEV가 비활성·오류·지연 상태여도 영상 분석·기본 경고·확인 기능은 동작해야 한다.
- AI가 정상이라고 답해도 진행 중 규칙 경고를 자동 해제하지 마라.
- 객체 미탐지·영상 끊김·분석 실패를 안전 확인으로 표시하지 마라.
- 위험 구역 밖 동물과 안전구역 안 사람의 규칙을 구분하는 현재 동작을 유지하라.
- 알림 확인, 사건 해소, 로그 보관, 스냅샷 보관을 서로 다른 상태로 취급하라.

## 4. 화면별 구현 요구

### SB-01 홈

- 긴 소개 영역보다 영상·미확인 알림을 먼저 보여준다.
- 영상 연결 수, 분석 정상 수, 진행 경고 수, 미확인 알림 수를 표시한다.
- 미확인 알림을 우선 표시하고 카메라·시각·심각도·확인 버튼을 제공한다.
- 카메라 요약을 클릭하면 해당 카메라 상세가 열린다.
- 최근 사진에서 스냅샷 상세와 연결 사건으로 이동할 수 있다.
- 알림이 없을 때 ‘미확인 알림 없음’을 표시한다. 오류가 있는데 ‘전체 안전’으로 표시하지 않는다.

### SB-02 카메라

- 4분할과 선택 카메라 1분할 전환, 영상 확대를 구현한다.
- 카메라마다 영상 관측 시각·분석 상태·ROI 감시 활성 여부를 표시한다.
- ROI 편집은 카메라 상세의 별도 영역으로 이동한다.
- 점 지정, 마지막 점 취소, 편집 초기화, 저장, 취소를 제공한다.
- ROI 표시 토글과 실제 감시 활성 설정을 분리한다.
- 편집 중 자동 갱신이 기준 프레임·꼭짓점·선택 카메라를 바꾸지 않게 한다.
- 저장 시 입력 범위를 검사하고 기존 세션·판단 무효화 절차와 연결한다.
- 탐지 제외 구역을 제공한다면 안전구역과 별도 필드·색상으로 저장하고 화면에 표시한다. 기본값은 없음이다.

### SB-03 알림

- ‘미확인 / 확인함 / 전체’와 카메라·심각도 필터를 제공한다.
- 사건 ID로 연결된 카드나 목록과 상세 패널을 만든다.
- 상세에는 증거 이미지, 사건 진행 상태, 해당 사건의 AI 참고 판단, 메모를 표시한다.
- 명시적 ‘확인했음’ 버튼으로 확인 상태를 저장한다. 상세를 열었다는 이유만으로 확인 처리하지 마라.
- 선택한 여러 알림의 확인 기능을 제공하되 표시 문자열 대신 사건 ID를 사용한다.
- 확인 취소가 가능하다면 취소 이력도 저장한다.
- 오탐 표시는 검토 기록으로 저장하고 자동 학습·자동 제외 구역 생성으로 연결하지 않는다.
- 재시작·다른 브라우저 접속 이후에도 확인 상태가 유지되어야 한다.
- 확인한 진행 사건은 진행 경고로 남고, 재발한 새 사건은 미확인으로 시작한다.

### SB-04 이벤트 로그

- 날짜 범위·카메라·심각도·사건 종류·확인 상태로 검색한다.
- 발생 시각, 객체, 사건 종류, 진행 상태, 확인 상태를 표시한다.
- 행 선택 시 동일 사건의 상세·스냅샷·보조 판단을 연결한다.
- 사건의 실제 종료 사유를 표시한다. 추적 소실과 안전 복귀를 동일하게 표시하지 마라.
- ‘필터 초기화’, ‘로그 목록 비우기’, ‘보관된 로그 보기’, ‘복원’을 구분한다.
- 통계는 실제 발생 기준으로 보관 기록을 포함하고, 표의 현재 조회 건수와 구분해 라벨링한다.

### SB-05 스냅샷

- 전용 메뉴와 날짜·카메라·사건 종류 필터를 만든다.
- 화면 폭에 맞춰 약 2~4열 갤러리와 선택 기능을 제공한다.
- 큰 미리보기, 이전·다음 이동, 전체 화면 또는 원본 크기 확대를 제공한다.
- 1440×900 화면에서 큰 미리보기는 약 600px 높이를 시작점으로 조정한다.
- 카메라, 시각, 확인 상태, ‘사건 보기’를 함께 표시한다.
- 파일이 없으면 대체 안내와 사건 정보를 제공한다.
- 스냅샷 보관은 갤러리 기본 조회에만 적용한다. 사건 상세에서는 보관 상태와 함께 증거를 계속 확인할 수 있다.

### SB-06 AI 보조 판단

- 실제 제공자·모델명·비활성 여부를 명확히 표시한다. Ollama의 TEV를 JEV와 동일 모델로 표시하지 마라.
- 최신 요청 상태와 마지막 유효 결과를 별도로 관리한다.
- ‘현재 참고 / 당시 기록 / 요청 중 / 오류’와 응답 시각을 표시한다.
- 다른 카메라·다른 사건의 답을 현재 사건의 답으로 표시하지 마라.
- 원본 JSON은 접힌 개발 정보 영역으로 옮긴다.
- 기존 API 요청·응답 검증과 민감 정보 노출 방지를 유지한다.

### SB-07 설정과 공통 디자인

- 왼쪽 메뉴 약 220px, 작은 화면에서는 접기 가능하게 한다.
- 다크·밝은 테마, 브라우저별 기본 화면과 표시 밀도 설정을 제공한다.
- 스타일 토큰을 공통화하고 특정 AI 패널만 다크인 상태를 없앤다.
- 기본 디자인 예시: 배경 `#0F172A`, 카드 `#1E293B`, 본문 `#F1F5F9`.
- 색만으로 상태를 표현하지 말고 ‘경고 / 주의 / 오류 / 미확인’ 텍스트를 함께 사용한다.
- 키보드 포커스, 버튼 라벨, 텍스트 대비, 테이블 가로 넘침을 확인한다.
- 탐지 후보 기준·경고 확정 기준·확인 시간은 카메라별·클래스별로 설정하고 DB에 보존한다.
- 설정에는 단위·적용 카메라·시연용 기준 여부를 표시하고 변경 이력을 남긴다.

## 5. 로그·스냅샷 초기화의 정확한 동작

실제 삭제 대신 독립된 보관 상태를 구현하라.

```text
필터 또는 선택 목록 → 대상 미리보기 → 보관 실행
 → 기본 목록에서 제외 → 보관 목록에서 복원
```

필수 규칙:

1. 종료됐고 운영자가 확인한 사건만 기본 보관 대상이다.
2. 미리보기에서 실제 대상 ID를 확정하고 기간·카메라·건수를 표시한다.
3. 실행 시 해당 ID의 현재 자격을 트랜잭션 안에서 다시 확인한다. 자격이 바뀐 항목은 제외하고 결과를 알린다.
4. 새로 들어온 사건은 이전 미리보기 대상에 추가하지 않는다.
5. 로그 보관이 사진·ROI·AI 이력·확인 상태를 바꾸지 않는다.
6. 스냅샷 보관이 사건 로그·사진 파일을 삭제하지 않는다.
7. 복원은 각 보관 상태만 되돌린다.
8. 취소·빈 대상·중복 요청·오류를 처리하고 부분 처리 여부를 정확히 표시한다.
9. 운영 데이터에 대한 물리 삭제 버튼과 파일 삭제 코드는 이번에 추가하지 않는다.

미리보기 대상과 UI 필터·선택은 브라우저 세션별로 관리하고, 확인·보관 결과는 DB의 공유 상태로 관리하라.

## 6. 오탐 감소 구현

### 6.1 후보와 확정 객체를 분리

- 낮은 YOLO 탐지 점수는 후보 단계에 남기고 단일 후보만으로 사건을 만들지 않는다.
- 후보 채택 점수, 경고 확정 점수, 최소 관측 수·시간, 허용 누락 시간을 분리한다.
- 시간 계산은 단조 시계와 실제 관측 시각을 사용한다. 같은 프레임을 여러 번 처리해 확인 횟수를 늘리지 마라.
- 카메라·클래스별 설정을 적용하고, 모델 입력에서 이미 버린 탐지를 후처리 설정으로 복구할 수 있다고 가정하지 마라.
- 상태 예시: `candidate → confirmed → lost`. 실제 구조는 기존 추적기에 맞춰 단순하게 설계한다.

### 6.2 즉시 경고 우회 문제 해결

현재 `observe()`의 `exited or confirmed` 경로를 확인하라. `exited`가 후보 검증을 우회하면 `--confirm-sec`만 늘려도 오탐은 계속 발생한다.

- 먼저 안정적으로 확인된 객체인지 검사하고 구역 이탈 전환을 평가한다.
- 이전에 확인된 동물의 명확한 이탈은 빠르게 경고할 수 있게 한다.
- 처음부터 밖에서 관측된 후보와 실제 안→밖 전환을 구분한다.
- 즉시 경고를 전부 제거하거나 모든 객체에 긴 지연을 일괄 적용하지 마라.

### 6.3 경계 흔들림·제외 구역

- ROI 경계 주변의 완충 폭 또는 진입·이탈 확인 시간을 적용한다.
- 완충 폭의 단위를 명시하고 영상 크기 변경에도 의미가 유지되게 한다.
- 동일 사건 중복을 억제하고 안정적인 안전 복귀 뒤 재발하면 다시 알린다.
- 탐지 제외 구역 기능은 운영자가 직접 검토·저장한 경우에만 적용한다. 특정 나무 위치를 코드에 하드코딩하지 마라.
- 멈춘 동물도 있으므로 움직임이 없다는 이유만으로 동물 탐지를 제거하지 마라.
- 반복되는 고신뢰도 나무 오탐은 지속 시간 검사로 해결되지 않을 수 있다는 한계를 README에 기록한다.

### 6.4 검증 지표

가능한 동일 영상 묶음으로 변경 전후를 비교하라: 정상 동물, 실제 이탈, 나무 흔들림, 가림, 경계 이동, 사람 진입.

- 오경보 건수/카메라 시간.
- 실제 사건 탐지 비율과 놓친 사건 수.
- 첫 위험 관측부터 경고까지의 지연.
- 중복 사건 수와 실제 분석 FPS.

초기 수치는 시연용이라고 표시하고 검증 없이 ‘오탐 해결’ 또는 정확도 개선 수치를 주장하지 마라. 평가 영상이 없으면 검증 도구·절차와 합성 관측 테스트를 제공하고 실제 영상 평가는 미실시로 표시하라.

## 7. 데이터와 코드 구성

다음 정보가 사건 ID로 연결되도록 확장하라. 동일 의미의 기존 필드가 있으면 재사용하라.

| 영역 | 필요한 데이터 |
|---|---|
| 사건 | 기존 ID, 발생 시각, 카메라, active, ended_at, end_reason, row_json |
| 확인 | acknowledged_at, 확인·취소 이력, 가능하면 확인자 표시명 |
| 검토 | review_label, review_note, 검토 시각 |
| 보관 | log_archived_at, snapshot_archived_at, 변경 이력 |
| 탐지 설정 | 카메라·클래스별 기준, 버전, 변경 전후 값·시각 |

- 현재 `Database.events()`가 `row_json`만 반환한다면 새 화면용 조회 함수를 추가해 사건 ID와 상태를 포함하라.
- 기존 통계·표가 기대하는 컬럼 계약을 유지하거나 어댑터를 제공하라.
- 모든 조회는 명시적 날짜·필터를 지원하고 필요한 인덱스·페이지 단위를 적용하라.
- 확인 동작은 멱등적으로 처리하고 중복 클릭 때문에 잘못된 건수가 발생하지 않게 하라.
- 사진 파일을 DB 트랜잭션 안에서 장시간 읽거나, 분석 락을 잡은 채 UI 조회를 오래 수행하지 마라.
- 무거운 이미지 변환과 DB 전체 조회를 모든 타이머에서 반복하지 마라.
- 숨겨진 화면의 불필요한 갱신을 줄이고, 탐지 엔진은 화면 전환과 무관하게 동작하게 하라.
- 기존 0.2초 영상 갱신과 2초 통계 갱신의 역할을 검토하되 실제 추론 FPS와 UI 주기를 혼동하지 마라.

권장 변경 연결:

| 현재 함수·영역 | 구현 책임 |
|---|---|
| `build_app()` | 사이드바, 화면별 컴포넌트·이벤트 |
| `original.refresh_all` 연결 | 화면별 데이터 갱신과 상태 유지 |
| `JEV_CSS` / `load_css()` | 공통 테마·가시성 개선 |
| `Database` | 마이그레이션, 조회, 확인, 보관, 복원 |
| `alert_banner()` | 진행 경고와 미확인 알림의 정확한 표현 |
| `detect()` / `IoUTracker` | 후보 품질·관측 지속성 |
| `observe()` | 후보 확정·경계 전환·사건 생성 |
| `jev_view()` | 사건별 AI 보조 결과와 최신성 |

필요한 만큼만 모듈화하고 전체 앱 구조를 불필요하게 교체하지 마라.

## 8. 구현 순서

1. 실제 코드·의존성·기존 테스트·변경 사항을 확인하고 재현 가능한 실행 명령을 확보한다.
2. 기존 데이터 복사본으로 마이그레이션과 사건 ID 기반 조회를 구현한다.
3. 사이드바·전체 테마·화면 분리를 구현한다.
4. 알림 확인·메모·오탐 표시와 홈·사이드바 건수 연결을 구현한다.
5. 로그·스냅샷의 필터·상세·보관·복원을 구현한다.
6. 카메라 상세·ROI 편집·설정 영속화를 연결한다.
7. 후보 확정·경계 흔들림 억제와 관련 테스트를 구현한다.
8. 기존 AI 보조 판단과 새로운 사건 상세를 연결하고 통합 검증한다.
9. README와 검증 보고서를 작성한다.

## 9. 필수 검증

테스트는 임시 DB·임시 스냅샷·모의 AI 응답으로 실행하고 실제 운영 기록을 변경하지 마라.

### 자동 테스트

1. 기존 스키마에서 새 스키마로 마이그레이션 후 사건·ROI·AI 기록 보존, 반복 실행 가능.
2. 확인 처리·취소·중복 클릭·재접속 시 상태와 미확인 건수 일치.
3. 확인 처리가 사건 active와 종료 사유를 바꾸지 않음.
4. 미확인·진행 중 사건은 보관 대상에서 제외.
5. 미리보기 이후 새 사건 생성 또는 상태 변경이 발생해도 잘못 보관되지 않음.
6. 로그와 스냅샷 보관·복원이 서로 독립적이고 사진 파일을 보존.
7. 보관 후 새로고침해도 목록에 재등장하지 않음, 복원하면 정상 조회.
8. 가짜 사진 경로·누락 파일·빈 목록에서 오류 없이 대체 안내.
9. 낮은 신뢰도 단발 후보가 즉시 사건을 만들지 않음.
10. 확인된 실제 동물의 경계 통과는 경고하고, 첫 관측부터 밖인 경우와 구분.
11. 경계 흔들림은 중복 사건을 억제하고 안전 복귀 후 재발은 새 경고.
12. AI 비활성·실패 상태에서도 규칙 경고·확인 기능 정상 동작.
13. 기본 실행은 외부 AI 요청을 보내지 않고 가짜 결과를 표시하지 않음.

### 화면·실행 검증

- 1440×900과 더 좁은 화면에서 사이드바·카드·표·갤러리 확인.
- 다크·밝은 모드의 글자 대비, 선택·포커스 상태, 새로고침 후 테마 복원 확인.
- 1·4분할, 확대, 카메라 전환, ROI 편집 취소·저장 확인.
- 알림 상세·필터·선택이 자동 갱신으로 사라지지 않는지 확인.
- 다른 두 브라우저 세션에서 한쪽의 확인 결과가 다음 갱신에 반영되는지 확인.
- 홈·알림·사이드바의 미확인 수를 동일 범위로 계산하는지 확인.
- 사진 확대·로그 보관 중 분석 루프가 정지하지 않는지 확인.

실행 중인 사용자 서버를 임의로 종료하지 마라. 검증 서버가 필요하면 사용하지 않는 포트와 테스트 data-dir을 사용하라. 외부 공개 링크 생성·유료 API 호출·메시지 발송은 이 작업에 필요하지 않다.

도구나 의존성 제한으로 검증할 수 없는 항목은 이유와 재현 방법을 남기고, 가능한 다른 구현·검증은 계속하라. 실행하지 않은 테스트를 통과했다고 보고하지 마라.

## 10. 산출물과 완료 보고

제출할 내용:

1. 수정된 진입 파일과 필요한 신규 모듈·스타일 파일.
2. 기존 자료를 보존하는 스키마 마이그레이션.
3. 의미 있는 자동 테스트와 실행 결과.
4. 실행 명령, 화면 사용법, 보관·복원 의미, 설정 기준, 한계를 담은 README.
5. 화면 확인 자료와 가능한 오탐 비교 결과. 미실시 항목은 명시.

최종 보고 형식:

```text
구현 완료: 스토리보드 SB-01~07 / FP-01~03 중 실제 완료 항목
변경 파일: 경로와 핵심 변경
실행 방법: 실제 환경에서 확인한 명령
검증 결과: 자동 테스트 / 실행·화면 / 실제 영상 각각 구분
남은 제한: 미구현·미검증 항목과 이유
```

**완료 기준:** 왼쪽 메뉴로 화면을 이동하면서 영상을 감시하고, 발생한 알림을 확인해 상태를 저장하며, 로그·사진을 독립적으로 보관·복원할 수 있어야 한다. JEV는 보조 역할을 유지하고, 오탐 억제 변경은 실제 이탈의 누락·지연도 함께 점검해야 한다.

화면만 그려 놓고 버튼이 동작하지 않는 상태, 알림 확인이 메모리에만 남는 상태, 초기화가 원본 자료를 삭제하는 상태, 검증 없이 오탐이 해결됐다고 주장하는 상태는 완료로 보고하지 마라.
