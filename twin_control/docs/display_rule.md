# 영상 표시 기준 (v6 후보, R5)

2026-10-15 · 대상: 통합 관제 탭과 카메라 탭의 실영상 4채널

## 무엇이 바뀌었나

| 항목 | 이전 (v5) | v6 후보 |
| --- | --- | --- |
| 화면에 보내는 그림 | 분석이 끝난 프레임 (카메라당 초당 약 2~3장만 바뀜) | 최신 영상 프레임 (엔진이 초당 최대 15장 읽음) |
| 화면 갱신 주기 | 0.2초 | 0.1초 |
| 박스·글자 | 매번 새로 그림 | 분석 결과·구역·배너가 바뀔 때만 한 번 그려 두고 겹치기만 함 |
| 보는 사람 없는 카메라 | 매번 그리고 압축 | 그리지도 압축하지도 않음 |
| 탭을 바꿀 때 | 이전 영상 연결이 남아, 새 영상 칸이 검게 기다리는 경우가 있음 | 영상 칸을 지우기 전에 연결을 먼저 끊음 |

분석(YOLO 스레드, 구역 판정, 사건 기록)은 바꾸지 않았다. `twin_vision.LiveRenderer`는 엔진 상태를 읽기만 한다.

## 부드러움 기준

| 기준 | 값 | 확인 방법 |
| --- | --- | --- |
| 화면 갱신 | 4채널을 동시에 볼 때 카메라당 초당 8장 이상 | `/api/state`의 카메라별 `display_fps`, 또는 스트림 4개를 30초 받아 세기 |
| 멈춤 | 30초 동안 0.5초 넘게 멈추는 일 0회 | 같은 측정의 프레임 간격 |
| 분석 속도 | 같은 조건에서 이전 버전보다 낮지 않음 | `/api/state`의 카메라별 `fps` |
| 판정 | 이전 버전과 같음 | `twin_replay.py` 출력이 네 카메라 모두 글자 하나 다르지 않음 |
| 박스 위치 | 마지막 분석 프레임 기준. 1초 넘게 지난 결과에는 "이전 분석 결과 N초" 표시, 3초 넘으면 박스를 숨김 | 화면 확인 |
| 영상 반복 | 영상이 처음으로 돌아갈 때 한 번 끊기는 것은 허용 (시험 영상 특성) | |

## 측정 (2026-10-15, 같은 PC에서 다른 관제 서버 1대가 함께 도는 상태)

| | v5 | v6 후보 |
| --- | --- | --- |
| 화면 갱신 (카메라당) | 3.4장/초 (그나마 내용이 바뀌는 건 분석 속도만큼) | 8.9~9.1장/초 |
| 가장 긴 멈춤 | 0.72초, 0.5초 넘는 멈춤 2회 | 0.26초, 0회 |
| 분석 속도 | 1.2~1.3fps | 1.5~1.6fps |
| 재생 시험 (코끼리·기린·레서판다·호랑이) | 기준 | 네 카메라 모두 출력 동일 |

서버가 1대만 돌 때 v5의 분석 속도는 2.5~2.7fps, 화면은 3.7장/초였다.

## 개발 중 발견

- 처음에는 박스 층을 numpy 불리언 마스크로 겹쳤는데, 카메라당 약 16ms 동안 파이썬 실행 잠금(GIL)을 잡아 분석이 느려졌다. OpenCV `copyTo`(약 1.4ms, 잠금을 풂)로 바꿨다.

## 한계

- 박스는 마지막으로 분석한 프레임의 위치다. 영상은 최신이라, 걷거나 뛰는 대상과 박스가 분석 간격(약 0.4~0.7초)만큼 어긋나 보인다.
- 화면 압축이 카메라당 초당 약 9번으로 늘어 CPU를 조금 더 쓴다. 측정상 분석 속도는 떨어지지 않았지만, 다른 프로그램이 CPU를 많이 쓰면 확인이 필요하다.
- 브라우저 쪽 그리기(영상 디코딩)와 Cloudflare 터널로 볼 때의 전송량(약 2.5배)은 따로 재지 않았다.
